8. **Bonus cheat sheet** — UI panel + printable card (build in M8).
9. **Bonus on/off** — `config.bonusesEnabled` toggle; sim both variants.
10. **Win clarifications** — victory declared on own turn; board-exhaustion → points + tiebreak ladder.
11. **Solar Flare** added (4, play-on-draw) — all players +2 Power. *(Was not in v0.61; treated as a new card.)*
12. **Mines auto-drop on stack exhaustion**; purchase remains optional (price tunable).
13. **Stack composition** → config table (v0.61 numbers as defaults; third stack suspected bloated — tune via sim, don't guess).
14. **Card price** stays `#mines + 1` for now but lives in config; revisit formula after sim, especially given #12 makes mines arrive faster.
15. **Embezzlement** nerfed to a flat Sphere (default) — see OQ-2 (answered in #35: the flat Sphere is final).
16. **Output stays in the buffer; collection is meeple-gated and optional.** Operating a building (whether the active player's pending roll-factory or a round-end meeple operation) sends the product to the **output buffer** and leaves it there — it is never auto-collected to inventory. With a meeple on the building, the owner may **optionally** `COLLECT_OUTPUT` (output buffer → inventory, respecting caps) during their round-end turn; they may instead only load inputs, or decline entirely. Uncollected output stays in the buffer and may flow to a connected building's input. (Output **teleporters** remain the one exception — they divert the product straight to inventory on production.) This aligns the engine with the long-standing RULES.md output-access rule.
17. **Mine lean-hex outputs reduced 5 → 3, and the mine flow/​render geometry was reconciled.** The mine's second (lean) hex now has 3 ore outputs (one on every-other external edge) instead of 5. In the designer's numbering (counting from the shared edge) these are positions **#4, #8, #12**; internally they are 24-grid positions **15, 17, 23**. The shared/internal edge stays closed; the rich hex is unchanged.
    - **Geometry fix:** `adjAt` previously mapped the mine's hexes using the *normal* single-hex edge convention, which was rotated relative to how the renderer draws the mine. This was invisible on the symmetric rich hex (every external edge has ore) but, on the asymmetric lean hex, made the engine flow ore from different edges than the drawn ore-output dots — they even disagreed about which edge was the internal/shared one. `adjAt` now uses the mine's own edge convention (matching `drawMineHex1Points`), so the template, the renderer, and material flow all agree: ore flows from exactly the edges where the dots are drawn.
18. **Upgrades are never paid with materials; Production Increase is a 4-unit upgrade budget.** Confirmed rule: there is **no mechanism to exchange ore (or any material) for Control Module upgrades**. Upgrade-currency comes only from end-of-round free upgrades (= #mines), mine-slot-1 credits, and Production Increase.
    - The engine previously charged ore for the non-free portion of an upgrade (reachable via a Production Increase upgrade). That ore path is **removed** — upgrades are funded entirely by upgrade-currency (mine credits / PI budget / free upgrades), or they're illegal.
    - **Production Increase bug fixed:** it was modelled as "4 free claim/upgrade *actions*," so a PI **claim** placed *any* module ≥ the claim floor for one action at no cost (a bot claimed a building with module **#11** this way). It is now a budget of **4 upgrade-units** (`PRODUCTION_INCREASE_BUDGET`): a claim costs **(module − #mines + 1)** units, an upgrade costs the **numeric difference**, both drawn from the budget, still **≤1 claim** per turn. Claiming #11 with one mine would cost 11 units — far beyond the 4 granted — so it is now correctly rejected.
19. **Belts carry material through multi-belt chains; cross-player belt rules enforced at placement.**
    - **Chaining:** the flow resolver now propagates material along a chain of belts (mine/output → belt → belt → … → input), not just a single belt directly bridging source and input. Implemented as an input-driven search over the belt network. This is what makes the routing module (B1 `findRoute`) actually usable end-to-end.
    - **Belt routing module** (`engine/routing.ts`, `findRoute`): fewest-belt path from a source to an input; shared by the smart bot and (later) a human "route from A to B" helper.
    - **Placement constraints** (`applyPlaceBelt`, mirrored in `legalActions` and the router via shared `beltEndpointBlocked`): a belt endpoint may not connect across a shared edge to **another player's belt**, nor **block another player's claimed building input**. (The vaguer earlier "not adjacent to another player's buffers" is now this precise pair — input-blocking + belt-joining.)
20. **Output teleporters continuously drain to inventory (bug fix).** Previously an output teleporter only diverted material at the *moment of production* (`tryOperateFactory`). Material that entered an output buffer any other way — produced before the teleporter was placed, or overflow from when inventory was at the 6-cap and later had room — sat there permanently, and a full output buffer then blocked the factory from ever producing again. Now flow resolution (`drainOutputTeleporters`, run in `resolveDirectAdjacency`) also empties any teleported output buffer into its owner's inventory whenever there is room, respecting the cap. Output teleporters take priority over downstream belt/adjacency flow. Matches the RULES.md intent that material on an output teleporter goes to your inventory.
21. **Stack composition now scales with player count (bug fix — matches the rulebook).** `STACK_COMPOSITION` was a single fixed 96-piece placeholder applied to every player count; RULES.md S3 already specified `STACK_COMPOSITION[playerCount]`. It is now keyed by player count using the rulebook tables — **2p: 63 pieces (21/stack), 3p: 81 (27/stack), 4p: 96 (32/stack)** — and `buildStack`/`createGame` index by player count. Fewer players use fewer pieces, so low-count games no longer run overly long. (Balance note from the sim: because more players deplete the shared board faster, games shorten with player count — 4p ≈ 21 rounds — which is why the bot's slow meeple-loading strategy never reaches a 4-Tesseract win at 4p even though human belt/chain play can.)
22. **Factory recipes are now explicit data, enforced for loading *and* operating.** `config.FACTORY_RECIPES` lists each factory's exact valid input sets (Plate: Ore; Sphere: Ore+Plate / Plate+Plate; Tesseract: the five sets Ore+Plate+Sphere, Ore+Sphere+Sphere, Plate+Sphere+Sphere, Sphere³, Plate+Plate+Sphere). `factoryProduct` now matches the filled slots against this table instead of value-threshold math (the old `values[1]≥3 && values[2]≥7` test, which silently assumed the Plate/Sphere point values and also accepted a Tesseract as a high substitute input). Operating behaviour is unchanged for every legitimate recipe (verified equivalent) but is now robust to material-value tuning and rejects Tesseract-as-input. New `canLoadMaterial` (shared by `applyLoadBuildingInput`, `legalActions`, and the UI load buttons) only permits a load that keeps a valid recipe reachable — so you can no longer load a second Ore into a Sphere Factory, etc. Addresses the reported "invalid recipe" confusion and the request that recipe rules apply to loading as well as operating.
23. **Belt Weaver bonus now does real chain traversal (was a non-functional placeholder).** `findBeltWeaverHolder` previously counted `BELT_COUNT − beltsRemaining` (≤ the 5-belt supply, and it *miscounted bought belts*), so with the ≥8 threshold the bonus could never trigger. New `beltWeaver.longestBeltChain` computes the longest continuous chain of a player's belts: belts join across shared edges (seams, same geometry as flow), a claimed factory the player owns **bridges its input and output buffers** so a chain passes through it (the belts on each side count, the factory doesn't), and the chain must terminate at ≥2 buildings, or a mine + a building. Implemented by contracting seams/pass-throughs with union-find, then finding the longest simple path (by belt count) over the resulting belt-edge graph. The player-panel already shows a `★BeltWeaver` chip once held. Matches RULES.md's Belt Weaver definition (≥8 belts) and the reported 9-belt chain (8 belts into a Plate Factory + 1 from its output to a Tesseract Factory) that wasn't being credited.

24. **Mine lean-hex ore geometry fixed for all rotations (bug fix).** The mine's second (lean) hex has 3 ore outputs at *every-other* external edge. The rotation-0 mine (mine 1) rendered and flowed correctly, but rotated mines (mines 2 & 3, placed by players) put the 3 ore points on the wrong edges — two landed adjacent instead of alternating — because both the renderer (`drawMineHex1Points`) and the engine (`adjAt`) mapped the lean hex's template edges through a permutation that only yields the every-other pattern at rotation 0. Both now use a shared parity-correct mapping (`leanVertexEdge` in the renderer / `LEAN_OFFSET_TO_EDGE` in flow): the lean hex's internal edge sits at vertex edge `iv = HEX_DIR_TO_VERTEX_EDGE[rotation ^ 1]` and its 3 ore outputs at `{iv+1, iv+3, iv+5}` (opposite parity → alternating) for **every** rotation. Rotation-0 output is byte-for-byte unchanged (still ore at vertex edges 0/2/4), so mine 1, flow, and routing are unaffected; rotations 1–5 are corrected. This keeps render, the belt-route overlay (`connectionPointPixel`), and material flow (`adjAt`) consistent.

25. **Operating an activated factory is now the owner's explicit choice (resolves OQ-1).** A roll still activates every matching building on anyone's turn, but a FACTORY no longer auto-operates — each activated factory becomes a pending decision **for its owner**, who may **operate** (pay power + consume inputs) or **skip**. This stops another player's roll from silently spending your power/materials on plans you were saving them for. Implementation: `pendingFactoryOps` is now `{pieceId, ownerId}[]` (was active-player-only pieceIds); `resolveProduction` defers all owners' factories (power plants still auto-operate — no downside); `OPERATE_BUILDING`/`SKIP_FACTORY_ROLL` carry an optional `ownerId` so a non-active owner can resolve their own activation; `legalActions` returns a player's pending operate/skip regardless of turn; `END_ACTIONS` is blocked until every activation is resolved. The sim resolves all owners' activations each roll; `GameSession` settles bot activations immediately and, for humans, arms a **host-adjustable timeout** (`FACTORY_OP_TIMEOUT_MS`, default **8000 ms**) that defaults an undecided *off-turn* activation to operate-if-affordable (your own-turn activations wait for you). The action panel surfaces the operate/skip prompt for your factories even when it isn't your turn, with a clear "−X 🔋, −materials" label. Verified: operateChoice.test.ts, updated production/flow/teleporter tests, and the LAN integration test.

26. **Material flow is now recipe-aware (bug fix, extends #22).** Recipe validation previously governed only the manual `LOAD_BUILDING_INPUT` action; material arriving by mine adjacency or along belts (`fillInputsFromAdjacentMines` / `resolveDirectAdjacency`) filled any empty input slot regardless of recipe. That let a Sphere Factory end up holding two Ore (one placed manually, a second delivered by a mine/belt) — an invalid recipe it could never operate. Flow now checks `canLoadMaterial` before depositing into an input, so a unit only flows in if it keeps a valid recipe reachable — exactly the rule the manual load already followed. The recipe logic (`factoryProduct` / `canLoadMaterial`) moved to `rules/recipes.ts` so both `flow.ts` and `production.ts` share it without a circular import. Verified: flow.test.ts "mine ore flow is recipe-aware".

27. **Round-end turn is time-limited (multiplayer courtesy).** A player's round-end sequence (claiming buildings / upgrading Control Modules) now runs under a **host-adjustable timeout** (`ROUND_END_TIMEOUT_MS`, default **20 s**); if the player goes idle that long their round-end turn auto-ends (advances). The timer **resets on every action**, so an actively-playing player is never cut off, and it only applies to a human's turn (bots resolve immediately). Implemented in `GameSession` (a `<=0` timeout disables it, e.g. in tests); the client shows a live countdown, and the operate-choice prompt (#25) likewise shows a countdown while its off-turn timer runs. The remaining time rides along in the LAN `StateSnapshot` so clients count down without clock-skew.

28. **Scouting Drone: the legal-move list now offers every cell and rotation (consistency fix — no rule change).** `applyAction` already let the drawn piece go on any free cell adjacent to the board at any rotation (the same placements as a normal `PLACE_PIECE`), but `legalActions` listed each drone play only at the first such cell with rotation 0, so the UI and bots could not choose where or how to place it. `legalActions` now lists, for each piece it offers, every (cell × rotation) the engine accepts, using the same placement enumeration as `PLACE_PIECE` / `PLACE_OVERSTOCK_PIECE` (`tilePlacements`). What `applyAction` accepts is unchanged. (Still as before: the list offers the first 5 pieces of each available stack, while `applyAction` accepts any piece index — left for the owner to decide against RULES.md's "look through the draw pile, choose a piece".) Verified: legalActions.test.ts "Scouting Drone", flows.test.ts.

29. **Factory operations are listed only when the engine would accept them (consistency fix — no rule change).** When one building is claimed by two players and both Control Modules match the roll, each owner gets a pending operation. After the first owner operated it (output buffer now full), `legalActions` still offered `OPERATE_BUILDING` to the second owner, which `applyAction` refused (`CANNOT_OPERATE`). `legalActions` now offers a pending operation's operate only when `applyAction` would accept it (the skip is always offered). The same probe is used for the round-end meeple operation, which fixes the opposite gap there: an operation completed from inventory through the player's own input teleporter was accepted by the engine but not listed. What `applyAction` accepts is unchanged. Verified: legalActions.test.ts, the seeded every-player property test in sim.test.ts, and the controller soundness test (which no longer tolerates any engine refusal).

Building pieces used to allow belts only at #4, #5, #10, #11; the printed pieces have more holes. Now every hole on a building piece that is not an input or output is a belt point that **any** player may use, whoever has claimed the building — a claim never closes the belt points on the building's own piece. Hole positions were measured from the models (`public/models`, regenerated byte-for-byte from `Factory Speghetti AMS.3mf`, and re-measured on the full-resolution source meshes); none sits on an input or output:

    | Plate Factory | #3–#6, #9–#12 | #1 | #8 | #2, #7 |
    | Sphere Factory | #4–#6, #10–#12 | #1, #3 | #8 | #2, #7, #9 |
    | Tesseract Factory | #4, #5, #10, #11 (unchanged) | #1, #3, #12 | #8 | #2, #6, #7, #9 |

    New belt points: Plate Factory and Power Plant #3, #6, #9, #12; Sphere Factory #6, #12. `src/engine/__tests__/pieceModels.test.ts` fails if a template and its model ever disagree.

31. **Points facing a claimed building's inputs AND output are reserved for its owners (2026-11-21).** Previously a belt end was refused only when it faced the **input** of a building with a claim by *someone other than you* — which ignored outputs and wrongly blocked a co-owner. Now a belt end is refused when the point across the shared edge is an **input or output** of a building that has at least one claim and **none** of them is yours. Holding any claim on the building (alone or with others) lets you use the point; an unclaimed building's points are open to everyone. The refusal has its own code, `POINT_RESERVED`; joining another player's belt keeps `BELT_BLOCKED`. As before, the check applies only when a belt is placed: a belt already lying at such a point when another player claims the building later stays and keeps carrying material (this is what the engine already did for the input case: claiming, upgrading and Changing Priorities never touch belts; the only thing that removes belts other than their owner is Sink Hole, which returns the belts lying on the unclaimed piece it discards to their owners). `legalActions` and the belt router use the same check, and the router now lets a co-owner route into a building they share.

32. **Mines 2 and 3 have no ore exits on their lean hex (2026-11-21).** Every mine had ore exits at lean-hex positions 15, 17, 23; the printed Mines 2 and 3 have nothing on their lean hex (only Mine 1 has the two curved tracks there). Now only Mine 1 has lean-hex exits; Mines 2 and 3 release ore only from their rich hex, which on all three mines has exits on both points of its 5 external edges (positions 2–11, confirmed from the printed rays). Implemented as per-mine layouts (`MINE_LEAN_ORE_OUTPUTS` / `MINE_TEMPLATES` in `config.ts`, read through `pieceTemplate(piece)`), used by flow, routing, the Belt Weaver chain and the ore-connection estimate in `connectivity.ts` (which also stopped treating every hex next to a mine as ore-bearing).

33. **Drawing from a stack is a real step when there is a choice (2026-11-21).** For the feel of the face-down stacks, a player who has more than one open stack (unlocked and not empty) must first choose one with the new action `DRAW_PIECE { stackIndex }` and may then place only that stack's top piece; the draw cannot be changed. With one open stack nothing changes: its top piece is placed directly. A dropped Mine still takes priority (`PLACE_MINE`). New state field `drawnStackIndex` (null at the start of every place-a-piece step; absent in older saves, read as null). New pure helpers for the interface: `revealedStack(state)` (the stack whose top piece is face-up for everyone right now) and `upcomingTurnOrder(state)` (the order the round-end turns and the next round will use). Unchanged: Scouting Drone still looks through any open stack, Overstock Supplies still takes the top pieces of the lowest-numbered open stack, Sink Hole does not touch the stacks, and emptying a stack by any path still drops the next Mine.

34. **RULES.md belt text corrected to match the engine — documentation only, behaviour unchanged (2026-11-21).** Two sentences in the old belts paragraph described rules the engine never enforced. "One player's belt cannot feed another player's building": the engine has never checked who owns the belts along a chain — material flows from a source into whichever claimed building's input the chain reaches, whoever laid the belts. (What does stop you from laying a new belt into a building you hold no claim on is the reservation of its input and output points, #31.) "Must run mine→input or output→input": a belt that connects nothing is, and always was, a legal placement, and belts never lie on a mine; the sentence meant that material only moves along a chain that links a source to an input. RULES.md now says what the engine does. It also now states two consequences of the current engine explicitly, without a code change: a belt already lying at a reserved point stays when the claims on the building change later, in either direction (see OQ-7; answered in #38, which made such a belt end a dead end), and the one-belt-facing-a-Mine-per-turn limit counts every belt end that faces a Mine hex, ore exit or not (see OQ-8; answered in #39, which counts only ends facing an ore exit).

35. **The designer's answers that keep today's behaviour (OQ-1, OQ-2, OQ-3, OQ-5; 2026-11-24) — wording only.** OQ-1 was resolved by #25. **Embezzlement** stays the flat-Sphere version (#15); this is final, and RULES.md no longer calls it pending. **R&D Tax Write-Off**'s free teleporter is one of the player's 4 teleporters and, like any teleporter on the board, raises the teleporter price for everyone — what the engine already did. **Tuning** (#13 stack counts, #14 card price) stays in `config.ts`. No code behaviour changes; comments and RULES.md text were updated.

36. **Play-on-draw cards count toward the 2-cards-played limit (OQ-4, 2026-11-24).** Before: Overstock Supplies, Mine Inspection and Solar Flare, which resolve when drawn, did not count toward the 2 Leverage cards a player may play per turn. Now a play-on-draw card always resolves when drawn and uses up one of the turn's two plays if any are left; if none are left it resolves anyway. Buying cards is never blocked by the limit. Config toggle `PLAY_ON_DRAW_COUNTS_TOWARD_LIMIT` (default on), part of the rules fingerprint of saves.

37. **Teleporters come back when the claim is lost (OQ-6, 2026-11-24).** Before: a teleporter was permanent; if Changing Priorities moved a player's last Control Module off a building, their teleporter stayed bound to them, feeding or draining a building they no longer held, and kept counting toward the teleporter price. Now, as soon as a player holds no claim on a building, every teleporter of theirs on that building's buffers returns to their supply, the buffer has no teleporter, and the teleporter price (teleporters **currently on the board** + 1; `globalTeleporterCount` now means exactly that) drops accordingly. Material in the buffers stays. A player still can never remove a teleporter by choice. Implemented as one pure pass, `returnOrphanedTeleporters` (`rules/flow.ts`), run after every action, so any future effect that removes claims is covered too.

38. **An opponent's belt does not feed your building, and does not draw from it (OQ-7, 2026-11-24).** Before: a belt already lying at a point facing a building's input or output kept carrying material when the claims on the building changed later, so a former co-owner's belt (or a belt laid before someone else claimed the building) kept feeding or drawing from a building that was now someone else's. Now a belt end that faces, across the shared edge, an input or output of a building that has at least one claim, none of them the belt owner's, is a **dead end**: no material enters or leaves the belt chain through that end. This is the placement reservation of #31 (`POINT_RESERVED`) applied continuously to material flow, through one shared predicate, `isReservedPoint` (`rules/flow.ts`). A belt is still never removed by claim changes, and it works again as soon as its owner gains a claim on that building or the building becomes unclaimed. Direct adjacency (an output touching an input, no belt) is unchanged. Applied everywhere belt chains are followed: the flow resolver, the Belt Weaver chain (a dead end does not count as the chain reaching that building), and the table's flow display (`src/table/flowPath.ts`). The router (`routing.ts`) only plans new belts, which the placement rule already keeps off reserved points; the ore-connection estimate (`connectivity.ts`) does not follow existing belts — neither needed a change. Belts of different players cannot join (placement rule), so a chain has one owner.

39. **The one-Mine-belt-per-turn limit counts only ends facing an ore exit (OQ-8, 2026-11-24).** Before: any belt end facing a Mine hex counted, including points with no ore exit (all of the lean half of Mines 2 and 3, and the non-exit points of Mine 1's lean half). Now only a belt end that faces a Mine point whose role is `ore_output` counts (`beltEndpointFacesOreExit`, used by placement and `legalActions`).

40. **A pending factory decision of your own comes first; the online host accepts only listed moves (OQ-9, 2026-11-24).** Before: while the active player still had their own operate-or-skip decision pending, `legalActions` offered only operate and skip, but `applyAction` accepted other moves too (for example `PLACE_BELT`), and the online host checked moves with `applyAction` only. Now (1) the engine refuses every move except `OPERATE_BUILDING` / `SKIP_FACTORY_ROLL` while the active player has an entry of their own in `pendingFactoryOps` (code `DECISION_PENDING`; answering any owner's own pending entry stays allowed); and (2) the host (`session/hostSession.ts`) accepts a player's move only when `legalActions` lists it for that player (`isListedMove`, comparing the move's listed form with `sameMove`; the dice of a roll are filled in by the host and not compared; the owner of an operate-or-skip answer is stamped by the host with the sender's seat and then compared like any other field, so a player can answer only a decision of their own). The engine's own refusal is returned first, for its specific reason; a move the engine would take but the list does not offer is refused with `NOT_LISTED` ("That move is not available right now") and changes nothing. With every gap between the list and the engine closed (#41, #43), the seeded "accepted means listed" sweep in `sim.test.ts` now runs on all states, and a new sweep (`listedSweep.test.ts`) checks accepted ⇒ listed for every kind of move.

41. **Scouting Drone: any piece of any open stack, chosen by kind (2026-11-24).** Before: `legalActions` offered only the first 5 pieces of each stack, while `applyAction` accepted any index. The designer decided the rulebook's "look through the draw pile, choose a piece" means any piece. Pieces of one kind are alike, so the list now offers, for each open stack, one entry per kind of piece present in it (at its first index) × every placement; a play naming another index of the same kind takes the topmost piece of that kind (normalised in the engine, `scoutingDronePieceIndex`, so the effect is the same whichever copy is named, and `listedForm` maps it to the listed entry for the host).

42. **Paying keeps the highest materials (designer's report, 2026-11-24).** Before: a purchase spent the lowest materials first and returned all change as Ore (a Sphere + an Ore paying 3 left 5 Ore), and a teleporter had to be paid exactly (a player holding only a Sphere could not pay 3). Now every material payment (Leverage card, Mine, belt, teleporter) goes through `payMaterials` (`rules/flow.ts`, exported from the engine so the interface can preview what a purchase leaves): of every way of handing in whole units worth at least the price, the change comes back in materials strictly lower than the highest one handed in, largest first, up to the room under the 6-per-material cap (change that fits nowhere is lost); the outcome that loses the least to the cap and then leaves the most Tesseracts, Spheres, Plates, Ore (in that order) is chosen. Values come from `MATERIAL_VALUES`. Affordable ⇔ total value ≥ price, for teleporters too. Examples paying 3: Sphere + Ore → Plate + 2 Ore; Ore + Plate → Ore; 2 Spheres → Sphere + Plate + Ore; a Tesseract → 2 Spheres + 2 Plates; 3 Ore + a Tesseract → the Tesseract. (The reported "could not buy a Leverage card after placing belts" was checked in the engine: after placing, buying and undoing belts, 1 Ore + 1 Plate, or a lone Sphere, can buy a card at 2 Mines; no engine-side cause was found.)

43. **Moves the move list never offered are now refused by the engine too (consistency, 2026-11-24).** A broad sweep found these, each of which `applyAction` accepted although `legalActions` never listed it; the engine now agrees with the list: a **claim paid by nothing** (`CLAIM_BUILDING` without the Mine free claim or Production Increase was free in the actions step; now `UNFUNDED_CLAIM`); **Changing Priorities onto the same building** (it removed the claim and lost the Control Module; now `SAME_BUILDING`); **placing the meeple a second time** in a turn (`MEEPLE_ALREADY_PLACED`), on a Mine without choosing its resource or upgrade point, or with a Mine point on a building (`INVALID_MEEPLE_TARGET`); **ending the turn without placing the meeple** when it has somewhere to go (`MEEPLE_REQUIRED`; checked before the end-of-turn victory check, which also no longer accepts `END_TURN` outside the place-meeple step); running, loading or collecting from a building the meeple was recorded on with a Mine point (only reachable from older saves; `INVALID_TARGET`); a **Mine touching the board only with its lean hex** (now its rich hex must be next to the board; `NOT_ADJACENT`); a **rotation** other than a whole number 0–5 (`INVALID_ROTATION`). `EXCHANGE_MATERIALS` in the round-end turn was already listed and accepted (verified by a test). Moves that differ from a listed one only in form — belt ends in either order, a missing rotation (0), a flag set to false, a Leverage card choice the card does not use — count as that listed move (`canonicalAction`). *(The Mine rule is widened again in #47.)*

44. **When the pieces run out, the round is finished (designer's decision, 2026-11-24).** Before: the game ended at the end of the turn in which the last board piece was placed, so the later players of that round lost their turn and nobody had a round-end turn. Now, once every stack is empty and no Mine is waiting to be placed, play goes on until the round is complete: every remaining player takes their normal turn, the round-end turns are played, and then the game ends on points with the usual tie-break ladder (its "earliest in turn order" is the order the round-end turns just used). A player with nothing to draw skips the place-a-piece step: the turn goes straight on to the roll (`skipEmptyPlacePiece`, run after every move, so no turn is ever left without a move), and the 4-Tesseract win on your own turn still applies in those last turns. The end check moved from every `END_TURN` to the end of the last round-end turn (`checkBoardExhaustion`, using `piecesExhausted`: all stacks empty, no Mine waiting, no Overstock piece to place). Overstock Supplies with fewer than 3 pieces left draws what is left (none: nothing), and Scouting Drone can take the last piece and is not offered once none is left (both unchanged; now tested).

45. **A teleporter on an input lets its owner choose what to supply — for every building, Power Plants included (designer's decision, 2026-11-24).** What the engine did before (the designer asked to double-check it): when a building with its operator's teleporter on the input ran — a factory activated by a roll (answered with `OPERATE_BUILDING`, also by the host's 8-second default on another player's turn) or the meeple building at round end — and an input slot was empty, the engine itself picked materials from the operator's inventory (`findInputCompletion`: the first valid recipe in Ore → Plate → Sphere → Tesseract order, i.e. the cheapest) and took them, without asking. It did so only at that moment (and checked the same completion when deciding whether a roll's activation became a decision); nothing was ever pulled at other times, never with exchanging down, and only through the operator's own teleporter. A Power Plant ignored any teleporter: it ran at once on its roll, burning only what lay in its input. Now nothing is taken from an inventory unless its owner names it: `OPERATE_BUILDING` has an optional `supply: Material[]` — the materials taken from the operator's inventory through their input teleporter into the building's **empty** input slots as it runs (exactly one per empty slot, whole units held, a valid recipe together with what lies in the input; for a Power Plant one Ore, Plate or Sphere). A building whose input is empty can run entirely from the inventory this way; without a supply it runs only from its input. Refusals: `NO_INPUT_TELEPORTER` (no teleporter of the operator's on the input), `INVALID_SUPPLY` (not one material per empty slot), `INSUFFICIENT_MATERIAL` (not held), `INVALID_RECIPE` (no recipe; a Tesseract into a Power Plant). `legalActions` lists one `OPERATE_BUILDING` per distinct valid supply (sorted Ore, Plate, Sphere, Tesseract), plus the plain one when the building runs from its input alone (`operateSupplies`); `canonicalAction` / `sameMove` treat a missing and an empty supply alike and ignore its order. The round-end meeple operation takes the same field. **Power Plants:** one with its owner's teleporter on an **empty** input becomes a decision for that owner when activated (an entry in `pendingFactoryOps`, settled first on the owner's own turn like a factory's): run it with nothing supplied (the base Power Token) or with one material for the chart's tokens. It always runs, so **its skip is neither listed nor accepted** (`MUST_RUN`) — except once it can no longer run (its owner reached the Power Token cap since the roll), when only the skip is left. Every other Power Plant still runs at once. The host's timeout default (and its fallback when a bot fails) never supplies anything: it runs the building from its input when it can (a Power Plant: with nothing supplied), else skips. Output teleporters are unchanged.

46. **Short Sale and Changing Priorities cannot put a Control Module on another player's building (designer's decision, 2026-11-24).** Before: both could add a claim to a building another player had claimed, so one building could have two owners. Now they target only an unclaimed building or one the player already holds a claim on (still at most 3 of the player's claims per building); otherwise `ALREADY_CLAIMED`, and the list no longer offers it (`mayAddClaimByCard`). Two owners on one building no longer come about; older saves holding such a building still load and play (each owner holding a claim there may add to it, and every rule for shared buildings — pending decisions per owner, dead-end belts, teleporters returning — still applies).

47. **A Mine may touch the board with either half (designer's decision, 2026-11-24).** Reverses the Mine part of #43, which required the rich hex to be next to the board. A new Mine (bought or dropped) may now be placed wherever at least one of its two hexes is next to the board and neither overlaps a piece, in any of the six rotations. `minePlacementError` (engine) and `minePlacements` (the list for `PLACE_MINE` and `BUY_MINE`) agree; every such position and rotation is listed once.

48. **An empty Leverage deck is refilled from the discard pile (designer's decision, 2026-11-24).** Before: once the deck was empty no card could be bought (`DECK_EMPTY`), however full the discard pile. Now, when a card is bought and the deck is empty, the discard pile is shuffled into a new deck first. The shuffle uses the seeded RNG the state already carries (`state.rng`, which setup leaves behind and nothing else used), and advances it, so it is reproducible from the state alone and older saves need no new field. Buying is impossible only when deck and discard pile are both empty. New helpers `cardsLeftToDraw` and `nextCardDrawn` (the card a purchase will draw, after any reshuffle) for the interface and the move log.

49. **A Mine's upgrade point gives the number printed on that Mine (designer's decision, 2026-11-24).** Before: a meeple on any Mine's upgrade point earned (Mines in play + 1) Control Module upgrade credits. Now it earns the number printed on that Mine piece — 2 on Mine 1, 3 on Mine 2, 4 on Mine 3 — whatever the number of Mines in play (`MINE_UPGRADE_REWARDS` beside `MINE_RESOURCE_REWARDS` in `rules/mineRewards.ts`; `mineSlotReward` gives it to the interface). The Mine is told by its piece (`mine-1` … `mine-3`), which is also the order Mines come into play.

50. **Leverage cards may be played at any point of your own turn (designer's decision, 2026-11-24).** RULES.md already said "anytime on your turn", but the engine accepted `PLAY_CARD` only in the actions step. Now it is accepted, and listed, in all four steps of the active player's own turn — place a piece, roll, actions, place the meeple (before and after the meeple is down) — never in another player's turn, the setup claims or the round-end turns; still at most 2 per turn across the steps, and the active player's own pending operate-or-skip decision still comes first. Buying a card stays an actions-step move. Card by card, so every step stays sound: **Production Increase** may be spent (claim and upgrades) in any step of the turn it is played in, not only in the actions step; **Scouting Drone** in the place-a-piece step only before drawing (`ALREADY_DRAWN` after: the drawn piece is in the player's hand, and a Mine dropped by the drone could not replace a draw already made) — played before the draw, if it empties a stack and drops the next Mine, that Mine replaces the player's piece placement, and if it takes the last piece of all the step is skipped; **Changing Priorities** may not move the player's last Control Module off the building their meeple was placed on this turn (`MEEPLE_ON_BUILDING`; the meeple may stand only on a building of theirs). Sink Hole, Short Sale, Embezzlement, Net Surplus Sell-Off, Personal Jet Pack, Asset Forfeiture and R&D Tax Write-Off need no limit in any step.

51. **A building feeds only its own player's buildings (designer's decision, 2026-11-27).** Supersedes the last sentence of #38 ("Direct adjacency … is unchanged"). Before: a building's output touching the input of another building moved its material across whoever owned the two buildings, so one player's Plate Factory could feed another player's Sphere Factory. Now an output touching an input (no belt) moves material only when at least one player holds a claim on **both** buildings; otherwise nothing moves and the material stays in the output, blocked exactly as when the input is full (a factory with a full output cannot run again until it is emptied). Unchanged: an **unclaimed** building's output still passes into the claimed building it touches (it is nobody's material, as it is open to anyone's belt); an unclaimed building never receives; a Mine belongs to nobody and its ore exits fill any claimed building they touch; belt chains already stopped at buildings their owner holds no claim on (#38). One pure predicate, `directFlowAllowed(src, dst)` (`rules/flow.ts`, exported from the engine), is used by the flow resolver for every move of a building's output (direct contact, and as a safeguard every belt-chain delivery, where it changes nothing: a chain is one player's and its ends are dead ends at buildings that player holds no claim on), by the table's flow display (`flowPath.ts`, and the animation's fallback in `transition.ts`) and by the play-style bots' feed analysis (`feedAt`, judged as if the bot held the building it is weighing). The play-style bots' placement weights for an opponent's building touching a new piece's input (was +0.2) or output (was −0.6) are now neutral (0). No config toggle, as for the designer's other decisions; a game saved under the old rule loads and plays on under this one, and material that already moved into another player's input stays there.

52. **Picking up this turn's Mine belt frees the one-Mine-belt limit (consistency fix, 2026-11-27).** Before: `UNDO_BELTS` cleared the turn's Mine-belt mark, but `REMOVE_BELT` did not, so a player who picked up the one belt they had placed this turn facing a Mine ore exit still could not place another such belt that turn. Now, after `REMOVE_BELT`, the mark (`mineBeltPlacedThisTurn`) is set exactly when a belt still listed as placed this turn (`beltsPlacedThisTurn`) has an end facing a Mine ore exit, by the same test placement uses (`beltEndpointFacesOreExit`). Picking up a Mine belt placed on an earlier turn grants nothing: the player still has only this turn's one Mine belt. `legalActions` reads the same mark, so the list agrees.

## Open questions

- **OQ-10 (balance, for the designer; left open 2026-11-24):** the bot study (`docs/BOT_FINDINGS.md`, 4,935 simulated games on the current rules) finds that the Bonus Tesseracts decide most games — 78–96% of four-Tesseract wins use one, and a play style that goes for them wins 77.8% of 2-player and 58.5% of 3-player games — and that the Mine upgrade point is the main lever behind it: with the upgrade point giving 1 / 2 / 3 instead of the printed 2 / 3 / 4 (#49), a scripted bonus rush fell from 70.8% / 55.6% / 35.4% to 54.2% / 25.0% / 6.3% at 2 / 3 / 4 players (small samples, 24–48 games each).
