16. **Output stays in the buffer; collection is meeple-gated and optional.** Operating a building (whether the active player's pending roll-factory or a round-end meeple operation) sends the product to the **output buffer** and leaves it there — it is never auto-collected to inventory. With a meeple on the building, the owner may **optionally** `COLLECT_OUTPUT` (output buffer → inventory, respecting caps) during their round-end turn; they may instead only load inputs, or decline entirely. Uncollected output stays in the buffer and may flow to a connected building's input. (Output **teleporters** remain the one exception — they divert the product straight to inventory on production.) This aligns the engine with the long-standing RULES.md output-access rule.
17. **Mine lean-hex outputs reduced 5 → 3, and the mine flow/​render geometry was reconciled.** The mine's second (lean) hex now has 3 ore outputs (one on every-other external edge) instead of 5. In the designer's numbering (counting from the shared edge) these are positions **#4, #8, #12**; internally they are 24-grid positions **15, 17, 23**. The shared/internal edge stays closed; the rich hex is unchanged.
    - **Geometry fix:** `adjAt` previously mapped the mine's hexes using the *normal* single-hex edge convention, which was rotated relative to how the renderer draws the mine. This was invisible on the symmetric rich hex (every external edge has ore) but, on the asymmetric lean hex, made the engine flow ore from different edges than the drawn ore-output dots — they even disagreed about which edge was the internal/shared one. `adjAt` now uses the mine's own edge convention (matching `drawMineHex1Points`), so the template, the renderer, and material flow all agree: ore flows from exactly the edges where the dots are drawn.
18. **Upgrades are never paid with materials; Production Increase is a 4-unit upgrade budget.** Confirmed rule: there is **no mechanism to exchange ore (or any material) for Control Module upgrades**. Upgrade-currency comes only from end-of-round free upgrades (= #mines), mine-slot-1 credits, and Production Increase.
    - The engine previously charged ore for the non-free portion of an upgrade (reachable via a Production Increase upgrade). That ore path is **removed** — upgrades are funded entirely by upgrade-currency (mine credits / PI budget / free upgrades), or they're illegal.
    - **Production Increase bug fixed:** it was modelled as "4 free claim/upgrade *actions*," so a PI **claim** placed *any* module ≥ the claim floor for one action at no cost (a bot claimed a building with module **#11** this way). It is now a budget of **4 upgrade-units** (`PRODUCTION_INCREASE_BUDGET`): a claim costs **(module − #mines + 1)** units, an upgrade costs the **numeric difference**, both drawn from the budget, still **≤1 claim** per turn. Claiming #11 with one mine would cost 11 units — far beyond the 4 granted — so it is now correctly rejected.
19. **Belts carry material through multi-belt chains; cross-player belt rules enforced at placement.**
    - **Chaining:** the flow resolver now propagates material along a chain of belts (mine/output → belt → belt → … → input), not just a single belt directly bridging source and input. Implemented as an input-driven search over the belt network. This is what makes the routing module (B1 `findRoute`) actually usable end-to-end.
    - **Belt routing module** (`engine/routing.ts`, `findRoute`): fewest-belt path from a source to an input; shared by the smart bot and (later) a human "route from A to B" helper.
    - **Placement constraints** (`applyPlaceBelt`, mirrored in `legalActions` and the router via shared `beltEndpointBlocked`): a belt endpoint may not connect across a shared edge to **another player's belt**, nor **block another player's claimed building input**. (The vaguer earlier "not adjacent to another player's buffers" is now this precise pair — input-blocking + belt-joining.)
20. **Output teleporters continuously drain to inventory (bug fix).** Previously an output teleporter only diverted material at the *moment of production* (`tryOperateFactory`). Material that entered an output buffer any other way — produced before the teleporter was placed, or overflow from when inventory was at the 6-cap and later had room — sat there permanently, and a full output buffer then blocked the factory from ever producing again. Now flow resolution (`drainOutputTeleporters`, run in `resolveDirectAdjacency`) also empties any teleported output buffer into its owner's inventory whenever there is room, respecting the cap. Output teleporters take priority over downstream belt/adjacency flow. Matches the RULES.md intent that material on an output teleporter goes to your inventory.
21. **Stack composition now scales with player count (bug fix — matches the rulebook).** `STACK_COMPOSITION` was a single fixed 96-piece placeholder applied to every player count; RULES.md S3 already specified `STACK_COMPOSITION[playerCount]`. It is now keyed by player count using the rulebook tables — **2p: 63 pieces (21/stack), 3p: 81 (27/stack), 4p: 96 (32/stack)** — and `buildStack`/`createGame` index by player count. Fewer players use fewer pieces, so low-count games no longer run overly long. (Balance note from the sim: because more players deplete the shared board faster, games shorten with player count — 4p ≈ 21 rounds — which is why the bot's slow meeple-loading strategy never reaches a 4-Tesseract win at 4p even though human belt/chain play can.)
22. **Factory recipes are now explicit data, enforced for loading *and* operating.** `config.FACTORY_RECIPES` lists each factory's exact valid input sets (Plate: Ore; Sphere: Ore+Plate / Plate+Plate; Tesseract: the five sets Ore+Plate+Sphere, Ore+Sphere+Sphere, Plate+Sphere+Sphere, Sphere³, Plate+Plate+Sphere). `factoryProduct` now matches the filled slots against this table instead of value-threshold math (the old `values[1]≥3 && values[2]≥7` test, which silently assumed the Plate/Sphere point values and also accepted a Tesseract as a high substitute input). Operating behaviour is unchanged for every legitimate recipe (verified equivalent) but is now robust to material-value tuning and rejects Tesseract-as-input. New `canLoadMaterial` (shared by `applyLoadBuildingInput`, `legalActions`, and the UI load buttons) only permits a load that keeps a valid recipe reachable — so you can no longer load a second Ore into a Sphere Factory, etc. Addresses the reported "invalid recipe" confusion and the request that recipe rules apply to loading as well as operating.
23. **Belt Weaver bonus now does real chain traversal (was a non-functional placeholder).** `findBeltWeaverHolder` previously counted `BELT_COUNT − beltsRemaining` (≤ the 5-belt supply, and it *miscounted bought belts*), so with the ≥8 threshold the bonus could never trigger. New `beltWeaver.longestBeltChain` computes the longest continuous chain of a player's belts: belts join across shared edges (seams, same geometry as flow), a claimed factory the player owns **bridges its input and output buffers** so a chain passes through it (the belts on each side count, the factory doesn't), and the chain must terminate at ≥2 buildings, or a mine + a building. Implemented by contracting seams/pass-throughs with union-find, then finding the longest simple path (by belt count) over the resulting belt-edge graph. The player-panel already shows a `★BeltWeaver` chip once held. Matches RULES.md's Belt Weaver definition (≥8 belts) and the reported 9-belt chain (8 belts into a Plate Factory + 1 from its output to a Tesseract Factory) that wasn't being credited.

24. **Mine lean-hex ore geometry fixed for all rotations (bug fix).** The mine's second (lean) hex has 3 ore outputs at *every-other* external edge. The rotation-0 mine (mine 1) rendered and flowed correctly, but rotated mines (mines 2 & 3, placed by players) put the 3 ore points on the wrong edges — two landed adjacent instead of alternating — because both the renderer (`drawMineHex1Points`) and the engine (`adjAt`) mapped the lean hex's template edges through a permutation that only yields the every-other pattern at rotation 0. Both now use a shared parity-correct mapping (`leanVertexEdge` in the renderer / `LEAN_OFFSET_TO_EDGE` in flow): the lean hex's internal edge sits at vertex edge `iv = HEX_DIR_TO_VERTEX_EDGE[rotation ^ 1]` and its 3 ore outputs at `{iv+1, iv+3, iv+5}` (opposite parity → alternating) for **every** rotation. Rotation-0 output is byte-for-byte unchanged (still ore at vertex edges 0/2/4), so mine 1, flow, and routing are unaffected; rotations 1–5 are corrected. This keeps render, the belt-route overlay (`connectionPointPixel`), and material flow (`adjAt`) consistent.

25. **Operating an activated factory is now the owner's explicit choice (resolves OQ-1).** A roll still activates every matching building on anyone's turn, but a FACTORY no longer auto-operates — each activated factory becomes a pending decision **for its owner**, who may **operate** (pay power + consume inputs) or **skip**. This stops another player's roll from silently spending your power/materials on plans you were saving them for. Implementation: `pendingFactoryOps` is now `{pieceId, ownerId}[]` (was active-player-only pieceIds); `resolveProduction` defers all owners' factories (power plants still auto-operate — no downside); `OPERATE_BUILDING`/`SKIP_FACTORY_ROLL` carry an optional `ownerId` so a non-active owner can resolve their own activation; `legalActions` returns a player's pending operate/skip regardless of turn; `END_ACTIONS` is blocked until every activation is resolved. The sim resolves all owners' activations each roll; `GameSession` settles bot activations immediately and, for humans, arms a **host-adjustable timeout** (`FACTORY_OP_TIMEOUT_MS`, default **8000 ms**) that defaults an undecided *off-turn* activation to operate-if-affordable (your own-turn activations wait for you). The action panel surfaces the operate/skip prompt for your factories even when it isn't your turn, with a clear "−X 🔋, −materials" label. Verified: operateChoice.test.ts, updated production/flow/teleporter tests, and the LAN integration test.

26. **Material flow is now recipe-aware (bug fix, extends #22).** Recipe validation previously governed only the manual `LOAD_BUILDING_INPUT` action; material arriving by mine adjacency or along belts (`fillInputsFromAdjacentMines` / `resolveDirectAdjacency`) filled any empty input slot regardless of recipe. That let a Sphere Factory end up holding two Ore (one placed manually, a second delivered by a mine/belt) — an invalid recipe it could never operate. Flow now checks `canLoadMaterial` before depositing into an input, so a unit only flows in if it keeps a valid recipe reachable — exactly the rule the manual load already followed. The recipe logic (`factoryProduct` / `canLoadMaterial`) moved to `rules/recipes.ts` so both `flow.ts` and `production.ts` share it without a circular import. Verified: flow.test.ts "mine ore flow is recipe-aware".

27. **Round-end turn is time-limited (multiplayer courtesy).** A player's round-end sequence (claiming buildings / upgrading Control Modules) now runs under a **host-adjustable timeout** (`ROUND_END_TIMEOUT_MS`, default **20 s**); if the player goes idle that long their round-end turn auto-ends (advances). The timer **resets on every action**, so an actively-playing player is never cut off, and it only applies to a human's turn (bots resolve immediately). Implemented in `GameSession` (a `<=0` timeout disables it, e.g. in tests); the client shows a live countdown, and the operate-choice prompt (#25) likewise shows a countdown while its off-turn timer runs. The remaining time rides along in the LAN `StateSnapshot` so clients count down without clock-skew.

28. **Scouting Drone: the legal-move list now offers every cell and rotation (consistency fix — no rule change).** `applyAction` already let the drawn piece go on any free cell adjacent to the board at any rotation (the same placements as a normal `PLACE_PIECE`), but `legalActions` listed each drone play only at the first such cell with rotation 0, so the UI and bots could not choose where or how to place it. `legalActions` now lists, for each piece it offers, every (cell × rotation) the engine accepts, using the same placement enumeration as `PLACE_PIECE` / `PLACE_OVERSTOCK_PIECE` (`tilePlacements`). What `applyAction` accepts is unchanged. (Still as before: the list offers the first 5 pieces of each available stack, while `applyAction` accepts any piece index — left for the owner to decide against RULES.md's "look through the draw pile, choose a piece".) Verified: legalActions.test.ts "Scouting Drone", flows.test.ts.

29. **Factory operations are listed only when the engine would accept them (consistency fix — no rule change).** When one building is claimed by two players and both Control Modules match the roll, each owner gets a pending operation. After the first owner operated it (output buffer now full), `legalActions` still offered `OPERATE_BUILDING` to the second owner, which `applyAction` refused (`CANNOT_OPERATE`). `legalActions` now offers a pending operation's operate only when `applyAction` would accept it (the skip is always offered). The same probe is used for the round-end meeple operation, which fixes the opposite gap there: an operation completed from inventory through the player's own input teleporter was accepted by the engine but not listed. What `applyAction` accepts is unchanged. Verified: legalActions.test.ts, the seeded every-player property test in sim.test.ts, and the controller soundness test (which no longer tolerates any engine refusal).

30. **Belt connection points on building pieces follow the printed pieces (2026-11-21).** The designer decided the current printed pieces are the source of truth for where belts connect. Building pieces used to allow belts only at #4, #5, #10, #11; the printed pieces have more holes. Now every hole on a building piece that is not an input or output is a belt point that **any** player may use, whoever has claimed the building — a claim never closes the belt points on the building's own piece. Hole positions were measured from the models (`public/models`, regenerated byte-for-byte from `Factory Speghetti AMS.3mf`, and re-measured on the full-resolution source meshes); none sits on an input or output:

    | Piece | Holes (= belt points) | Inputs | Output | No hole |
    |---|---|---|---|---|
    | Blank | #1–#12 | – | – | – |
    | Plate Factory | #3–#6, #9–#12 | #1 | #8 | #2, #7 |
    | Sphere Factory | #4–#6, #10–#12 | #1, #3 | #8 | #2, #7, #9 |
    | Tesseract Factory | #4, #5, #10, #11 (unchanged) | #1, #3, #12 | #8 | #2, #6, #7, #9 |
    | Power Plant | #3–#6, #9–#12 | #1 | – | #2, #7, #8 |
    | Mines 1–3 | none | – | – | all |

    New belt points: Plate Factory and Power Plant #3, #6, #9, #12; Sphere Factory #6, #12. `src/engine/__tests__/pieceModels.test.ts` fails if a template and its model ever disagree.

31. **Points facing a claimed building's inputs AND output are reserved for its owners (2026-11-21).** Previously a belt end was refused only when it faced the **input** of a building with a claim by *someone other than you* — which ignored outputs and wrongly blocked a co-owner. Now a belt end is refused when the point across the shared edge is an **input or output** of a building that has at least one claim and **none** of them is yours. Holding any claim on the building (alone or with others) lets you use the point; an unclaimed building's points are open to everyone. The refusal has its own code, `POINT_RESERVED`; joining another player's belt keeps `BELT_BLOCKED`. As before, the check applies only when a belt is placed: a belt already lying at such a point when another player claims the building later stays and keeps carrying material (this is what the engine already did for the input case: claiming, upgrading and Changing Priorities never touch belts; the only thing that removes belts other than their owner is Sink Hole, which returns the belts lying on the unclaimed piece it discards to their owners). `legalActions` and the belt router use the same check, and the router now lets a co-owner route into a building they share.

32. **Mines 2 and 3 have no ore exits on their lean hex (2026-11-21).** Every mine had ore exits at lean-hex positions 15, 17, 23; the printed Mines 2 and 3 have nothing on their lean hex (only Mine 1 has the two curved tracks there). Now only Mine 1 has lean-hex exits; Mines 2 and 3 release ore only from their rich hex, which on all three mines has exits on both points of its 5 external edges (positions 2–11, confirmed from the printed rays). Implemented as per-mine layouts (`MINE_LEAN_ORE_OUTPUTS` / `MINE_TEMPLATES` in `config.ts`, read through `pieceTemplate(piece)`), used by flow, routing, the Belt Weaver chain and the ore-connection estimate in `connectivity.ts` (which also stopped treating every hex next to a mine as ore-bearing).

33. **Drawing from a stack is a real step when there is a choice (2026-11-21).** For the feel of the face-down stacks, a player who has more than one open stack (unlocked and not empty) must first choose one with the new action `DRAW_PIECE { stackIndex }` and may then place only that stack's top piece; the draw cannot be changed. With one open stack nothing changes: its top piece is placed directly. A dropped Mine still takes priority (`PLACE_MINE`). New state field `drawnStackIndex` (null at the start of every place-a-piece step; absent in older saves, read as null). New pure helpers for the interface: `revealedStack(state)` (the stack whose top piece is face-up for everyone right now) and `upcomingTurnOrder(state)` (the order the round-end turns and the next round will use). Unchanged: Scouting Drone still looks through any open stack, Overstock Supplies still takes the top pieces of the lowest-numbered open stack, Sink Hole does not touch the stacks, and emptying a stack by any path still drops the next Mine.

34. **RULES.md belt text corrected to match the engine — documentation only, behaviour unchanged (2026-11-21).** Two sentences in the old belts paragraph described rules the engine never enforced. "One player's belt cannot feed another player's building": the engine has never checked who owns the belts along a chain — material flows from a source into whichever claimed building's input the chain reaches, whoever laid the belts. (What does stop you from laying a new belt into a building you hold no claim on is the reservation of its input and output points, #31.) "Must run mine→input or output→input": a belt that connects nothing is, and always was, a legal placement, and belts never lie on a mine; the sentence meant that material only moves along a chain that links a source to an input. RULES.md now says what the engine does. It also now states two consequences of the current engine explicitly, without a code change: a belt already lying at a reserved point stays when the claims on the building change later, in either direction (see OQ-7), and the one-belt-facing-a-Mine-per-turn limit counts every belt end that faces a Mine hex, ore exit or not (see OQ-8).
